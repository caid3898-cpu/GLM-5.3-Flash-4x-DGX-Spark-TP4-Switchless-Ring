## 3. ⚠️ 必读：这个模型会「先思考再回答」

GLM 的思考过程单独放在 `reasoning_content` 字段，**思考 token 计入 `max_tokens`**。

**症状**：`max_tokens` 给小了 → `content` 是 `null`、`finish_reason: "length"`。不是故障，是 token 被思考吃光了。

```python
max_tokens=2048            # 方案 A：给足
reasoning_effort="low"     # 方案 B（日常推荐）：可选 none|minimal|low|medium|high|xhigh|max
```

拿不到内容时**先调这个**，不要去查转发链路或网络。

## 4. 行为提示（重要变化，和旧双集群时代不同）

1. **不再是双副本**：所有请求共享同一个 TP4 模型。单路很快（c1），并发越高单路越慢（c8 时单路 prose ~28 tok/s），这是共享模型的正常行为，不是故障。
2. **前缀缓存很好**：相同 system prompt / 相同前缀的对话命中缓存后首 token 极快。请每轮带完整历史（标准做法），不要无状态轮询。
3. **长上下文强**：128K prefill ~40 秒（3450 tok/s），超长文档直接丢进来。

## 7. 出问题时怎么查

| 症状 | 大概率原因 | 怎么办 |
|---|---|---|
| `content` 是 `null` | 思考吃满 token | 加 `max_tokens` 或 `reasoning_effort:"low"`（§3） |
| HTTP 503 空响应、`Proxy-Connection` 头 | **本机代理把局域网请求劫持了**（v2rayN） | `env -u http_proxy -u https_proxy` 或代码里 pop 掉（§8） |
| HTTP 连接错误（kimi 等读**大写**变量的客户端） | `HTTP_PROXY`/`HTTPS_PROXY` 大写同样劫持 | `env -u HTTP_PROXY -u HTTPS_PROXY`（大小写全清） |
| HTTP 502/连接失败 | 集群或 LB 挂了 | `curl /health`；等 LB 自动探活恢复（~25 秒级） |
| 慢得离谱 | 并发打满了 | 降并发；单路应 prose ~58+ tok/s |
| 远程（tailscale）不通 | Mac/远端 tailscale 没开 | `tailscale up`；`tailscale status` 看在线 |

**容错**：LB 深度探针发现后端真挂了会把流量标记 down 并快速失败（不会干等）；恢复自动回切。

## 8. 一个环境层面的坑（Mac 上必看）

**在这台 Mac 上，Python 客户端调 `192.168.31.21` 可能一律 503，而 `curl` 正常。**

原因：macOS 系统代理（v2rayN）被 `urllib.request.getproxies()` 读到，把局域网地址塞进代理；curl 不读系统代理。

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY python3 your_client.py
# 或代码里
os.environ.pop("http_proxy", None); os.environ.pop("https_proxy", None)
```

**注意大小写**：干净 Terminal shell 里其实没有代理变量，问题只出现在继承了代理环境的场景（如从 ZCode 等带代理的 app 里再启动客户端）；kimi（Rust）这类客户端只读大写 `HTTP_PROXY`，只清小写不够。

**永久修复（2026-10-07 已上线）**：`~/.zshenv` 已把 `192.168.31.21`、`100-x-y-z` 幂等追加进 `no_proxy`/`NO_PROXY`，之后新开的任何 zsh（含 app 内置终端）都对集群直连，无需再手动 `env -u`。已在带 `HTTP_PROXY` 的环境下实测 kimi 走本地模型成功。不经过 zsh 的进程（如 GUI app 直启的守护）仍需手动清代理变量。

**判据**：同一地址 curl 通、Python 不通 → 先怀疑系统代理。
