### 8.1 多图链路调试备忘
- **测内网一定要用 `curl`，不要用 Python urllib**：本机 macOS 系统代理会让 urllib 访问内网返回 **503 空 body**，而 curl 正常 —— 会得出「集群坏了」的假结论。已在验证脚本里踩过一次。
- 构造多图请求用 `data:image/png;base64,...` 内联即可，无需起本地服务。
- 验证判据要**双向**：既要有「N 张被接受」（证明放宽生效），也要有「N+1 张被拒且报错写明 N」（证明不是无限制）。只看前者无法区分「真放到 N」和「关掉了限制」。
- ⚠️ **别拿模型的计数出字当上限判据**：测试图是循环复用的纯色图，模型数的是「能分辨几组图案」，会给出 126/62 这类值（见本节两次验证记录）。**上限是否生效只看 HTTP 状态码和 400 报错文案**，出字只用来确认请求「被处理了」而非「没被计数」。
- **大 payload 要在集群本机发**：128 张 12MP 图的 base64 请求体约 **395MB**，从 Mac 传 `curl -d @file` 会
  `curl: option -d: out of memory`（本机内存扛不住），传到集群本机后 curl 仍可能 OOM。
  正确做法是 scp 图片过去、在集群上本地拼 JSON 再打 localhost。
- ⚠️ **`curl: option -d: out of memory` 有两种成因，别混为一谈**：① 本机内存不足读不动 payload；
  ② 请求体过大本身就超了引擎处理能力。区分办法是看**引擎是否还活着**（`/health` 是否 200）——
  引擎活着 = 纯传输问题；引擎 000 = 引擎被打死了（见 8.3）。

### 8.2 图片会被自动压缩吗？——会，但 `max_pixels` 那个参数是无效的（2026-10-08 实测）

**结论：会压缩。** 机制在 `vllm/transformers_utils/processors/glm5next.py` 的 `smart_resize()`，在**像素预算**上双向缩放，缩放后的画布按 14px patch 对齐后换算成 token 数。

**实测每张图的 token 消耗（单图请求，prompt_tokens 含少量文本）**：

| 原图尺寸 | 像素 | prompt_tokens | 说明 |
|---|---|---|---|
| 224×224 | 0.05 MP | 84 | 几乎不缩 |
| 1024×768 | 0.79 MP | 1,056 | 近似线性 |
| **4000×3000** | **12 MP** | **4,090** | **被压到 4096 token 上限** |
| **8000×6000** | **48 MP** | **4,090** | **与 12MP 完全相同 ⇒ 确认封顶** |

**关键发现**：`--mm-processor-kwargs` 里的 **`max_pixels: 6422528` 根本没生效** —— 启动日志明确报
`Keyword argument 'max_pixels' is not a valid argument for this processor and will be ignored`。
真正封顶的是 **token 预算**：`max_image_tokens`，来自模型自带 `/model/processor_config.json`（默认 8000），
被启动参数覆盖为 **4096**（`--mm-processor-kwargs '{"max_image_tokens":4096}'`）。
所以「12MP 和 48MP 消耗完全相同」正是 token 封顶的证据；若是像素封顶，48MP 会被压到比 12MP 更小的画布。

⚠️ **别改 `max_pixels` 去「多塞点细节」—— 它是死的**。要调每图细节上限，改 `max_image_tokens`（代价：每图 token ×N，总预算同步暴涨）。

### 8.3 ⚠️ 128 张上限的另一面：大图多模态请求会**打死引擎**（实测事故）

**现象**：128 张 `4000×3000` 大图的请求，**32 张就把引擎打崩**了：
```
Worker proc VllmWorker-0 died unexpectedly (exit code: None), shutting down executor
→ EngineDeadError → 500 Internal Server Error → 引擎 /health 变 000
```
崩溃时 `prompt_token_ids_len=130319`（≈32 张 × 4070 tokens）。**16 张正常返回 200。**
多张 1024×768 中图（64/128 张）则直接让本机 `curl: option -d: out of memory`（payload 过大，与引擎无关）。

**根因**：崩溃不在 API 层而在 **worker 进程本身**（`exit code: None` = 被信号杀死，非 Python 异常）。
`dump_input.py` 显示每个 image feature 的 `pixel_values` 以 **bfloat16 全量常驻**
（`slices=[[slice(0,16280)]]`、`image_grid_thw=[1,110,148]`）。**压缩只省 token，不省处理期的像素内存**：
128 张 × 12MP 解码后的像素张量远超 GB10 的统一内存余量，worker 被 OOM 杀掉，连带整个 TP4 集群不可用。

**处置（已验证有效）**：`./start.sh stop` → 四台 `docker rm -f` → **`pkill -9 -f "VllmWorker"` 清孤儿进程** →
`./start.sh serve`。⚠️ 只 `docker rm` 不够：崩过的 worker 会以孤儿进程占住内存，
实测 `spark-0167` 只剩 **3.9 GiB MemAvailable**（正常应 >110），不清必然触发宿主 OOM-killer
（§1「44GiB 以上触发宿主 OOM-killer 实测四连」）。清理后四台回到 114-116 GiB 再启动，一次就成。

**给使用方的实际边界**（比 `MM_IMAGES=128` 这个数字重要得多）：

| 场景 | 实测结果 |
|---|---|
| 几十张 **1MP 以内**的截图（排障/GUI/视频抽帧典型量级） | 正常，1k tokens/张以内 |
| 十几张 **12MP 原始照** | 16 张正常，**32 张打死引擎** |
| 128 张 1MP 内截图 | 200 通过（上限按数量放行） |
| 单条请求总 tokens | 仍受 `MAX_MODEL_LEN=1048576` 约束 |

⇒ **`MM_IMAGES` 只管「张数」，不管「张数 × 尺寸」的乘积。** 上限放到 128 后，
真正的风险不再是那句 `At most N image(s)` 400（那是干净的拒绝），而是
**引擎被 OOM 打死、整个集群离线**（这是脏失败）。

### 8.4 图片自动压缩机制 `GLM_MM_MAX_SIDE=1024`（2026-10-08，根治 8.3 的问题）

**做法**：新增 `overlay/glm_mm_resize.py`，包装 processor 的 `smart_resize()` ——
**在任何缩放算尺寸之前**，先把超过上限的长边等比钳到 1024px。注册在 `overlay/sitecustomize.py`，
开关是 `GLM_MM_MAX_SIDE`（`EXTRA_ENV` 块内，px，0/留空=关闭），默认 1024。

**为什么钩 `smart_resize`**：它是 `vllm/transformers_utils/processors/glm5next.py` 里
**三个调用点的唯一入口**（preprocess、placeholder 计数、逐图 token 记账），
包一层就覆盖全部路径；只改传进去的 `(h, w)`，对齐与预算逻辑全部留给上游。
对齐因子 `ALIGN=28`（`patch_size 14 × merge_size 2`），缩放后取 28 的倍数，不改变上游的对齐行为。
**小图原样通过**（只钳上限、不放大），所以日常 1MP 以内的截图完全不受影响。

**实测效果（单图 prompt_tokens）**：

| 原图 | 压缩前 | 压缩后 | 降幅 |
|---|---|---|---|
| 224×224 (0.05MP) | 84 | 81 | ~0（对齐取整差值） |
| 1024×768 (0.79MP) | 1,056 | 1,053 | ~0 |
| **4000×3000 (12MP)** | **4,090** | **1,016** | **-75%** |
| **8000×6000 (48MP)** | **4,090** | **1,016** | **-75%** |

**端到端验证**：**32 张 12MP 从「500 打死引擎」变成 200 通过**（32,047 tokens）——
这正是 8.3 里崩掉的同一个规模。小图 token 不变，引擎存活。

**⚠️ 仍然存在的边界（诚实记录）**：**128 张 12MP 依然会打死引擎**（实测 500 + `/health` 变 000，已恢复）。
压缩把每张降到 1016 tokens，128 张也只占 1M 上下文的 12.4% —— 但仍会崩。
⇒ **瓶颈不是上下文长度，是视觉编码后像素张量的并发驻留总量。**
GB10 统一内存要同时装 194.5 GiB 权重 + 24 GiB KV 池 + 图像张量，余量本就有限。
**实测安全线：单条请求 ≤32 张大图**；日常 1MP 内的截图不受此限（张数按 `MM_IMAGES=128` 放行）。
真要一次发上百张大图，需先把长边压到 512 左右（token 与像素同时降一个量级）。

**调参**：`GLM_MM_MAX_SIDE` 是像素上限。想更稳就调小（512 = 极端省，小字会糊）；
想保细节就调大（2048 = 几乎无损，但内存压力回到压缩前）。改完要重启集群。

**部署时踩的两个坑**：
1. `start.sh:89` 是 `for kv in ${EXTRA_ENV}` —— **`EXTRA_ENV` 块内绝对不能写注释**，
   每一行都会被拆成 `-e $kv`，中文注释会变成 `-e 图片长边像素上限…` 直接让 `docker run` 报
   `flag needs an argument: 'e'`、容器根本起不来。注释只能写在块外。
2. 变量写在 `EXTRA_ENV` 块**外**的裸赋值不会传进容器（`printenv GLM_MM_MAX_SIDE` 为空、钩子不 armed），
   极易误判成「钩子没生效」。验证要两处都查：`docker exec … printenv` + 日志里的
   `glm-mm-resize: armed max_side=1036px align=28`（1036 = 1024 向上对齐到 28 的倍数）。

### 8.5 多图链路调试备忘（跨小节通用）
- **测内网一定要用 `curl`，不要用 Python urllib**：本机 macOS 系统代理会让 urllib 访问内网返回 **503 空 body**，而 curl 正常 —— 会得出「集群坏了」的假结论。
  ⚠️ 例外：**大 payload（数百 MB）在集群本机也不能用 curl** —— GB10 统一内存要和引擎抢，
  curl 读 395MB 会 `option -d: out of memory`（此时要看引擎 `/health` 判断是传输问题还是引擎死了）。
  超大 payload 改用 Python `http.client` 分块流式发（见 8.4 验证记录）。
- 构造多图请求用 `data:image/png;base64,...` 内联即可，无需起本地服务。
- 验证判据要**双向**：既要有「N 张被接受」（证明放宽生效），也要有「N+1 张被拒且报错写明 N」（证明不是无限制）。只看前者无法区分「真放到 N」和「关掉了限制」。
- ⚠️ **别拿模型的计数出字当上限判据**：测试图是循环复用的纯色图，模型数的是「能分辨几组图案」，会给出 126/62 这类值。**上限是否生效只看 HTTP 状态码和 400 报错文案**，出字只用来确认请求「被处理了」。
- **写验证脚本时中文标点紧跟 `$var` 会炸**：bash 把 `（$tok，` 里的 `$tok，` 当成一个变量名去展开，
  在 `set -u` 下报 `tok: unbound variable`。凡变量后面紧跟中文标点，一律写成 `${tok}`。
  同理 `2>&1` 混进管道解析器会让 `cut -f1` 拿到非数字 —— 判据脚本里不要给 curl 加 `2>&1`。
- 轮询 `/health` 等加载时别预设时长：实测都是 ~170s，但按 10s 步长轮询并打印 try 序号，可以在超时后一眼看出卡在哪一段。

### 8.6 ⚠️ 事故：bf94 内存耗尽 → LB 被 OOM 反复杀 → ZCode「没反应」（2026-10-08 17:50）

**症状**：用户报 ZCode 接本地模型「对话没反应」。前门 `:8002/health` 返回 **503**，
`healthy=false`、`deep_err="stream idle 30s"`、`reaped_streams=1`。
**但引擎直连 8093 完全正常**：200、出字 OK、`num_requests_running=0`、队列全空。
⇒ **问题在代理层，不在模型**。

**根因链**（`journalctl --user -u glm53-lb` 给出了完整因果）：
```
17:49:49  [lb] shallow A: True -> False
17:50:02  [lb] A 回源流 30s 零字节 → 判疑似卡死
17:50:32  glm53-lb.service: A process of this unit has been killed by the OOM killer
17:50:38  Scheduled restart job, restart counter is at 1      ← 崩溃循环开始
17:50:46  POST /v1/chat/completions 200 OK
17:51:16  [lb] health A: True -> False ... stream idle 30s
17:51:49  Main process exited, code=killed, status=9/KILL
```
LB 在 17:49→17:51 连续被杀 3 次，每次起来十几秒又倒。**ZCode 连的是 8002，所以表现为「没反应」**。

**为什么 LB 是那个被杀的**：rank0(bf94) 除引擎外还跑着 LB、网关、grafana、prometheus、两个 exporter，
是四台里最挤的；内存紧张时 OOM-killer 按 RSS 挑人，LB 成了倒霉的那个。
`glm-memguard`（旧双集群时代的看门狗，每 10 分钟 `drop_caches`）并不能真正释放那 101 GiB。

**内存账本（rank0，实测）**：
| 项 | 大小 |
|---|---|
| 总内存 | 121.7 GiB |
| GPU 统一内存（引擎权重 48.6 + KV 池 40 + 工作区） | **101.1 GiB（83%）** |
| 系统其余（内核/dockerd/LB/grafana…挤这点） | 20.6 GiB |
| 崩溃时 MemAvailable | **81 MiB** |

**处置（两步）**：
1. **止血**：给 LB 加 drop-in `~/.config/systemd/user/glm53-lb.service.d/memguard.conf`
   ```
   [Service]
   MemoryMax=512M
   MemorySwapMax=0
   ```
   让内核在自身 OOM 前先回收 LB，而不是随机杀掉它。实测 `NRestarts` 从持续增长变成 **0**。
   ⚠️ 注意 `memguard.conf` 这个名字与旧的 `glm-memguard-a.service`（看门狗）**不是一回事**，容易混淆。
2. **根治**：**`KV_BYTES` 40GiB → 28GiB**（`current.env`，备份 `.bak-kv28-20261008`）。
   监控栈砍掉毫无意义 —— grafana 96MB + prometheus 73MB + exporters 27MB ≈ **200MB**，
   而 KV 池每台占 40 GiB。**唯一有效的杠杆就是 KV 池。**
   代价：KV 池 4,491,538 tokens，满 1M 上下文的并发从 **6.12x → 4.28x**（单用户场景绰绰有余）。

**实测收益（处置前后对比）**：

| 指标 | 处置前（崩溃时） | 处置后 |
|---|---|---|
| bf94 `MemAvailable` | **81 MiB** | **15.2 GiB**（+190 倍） |
| GPU 统一内存占用 | 101.1 GiB | **87.2 GiB**（-14 GiB） |
| KV 池并发（满 1M） | 6.12x | 4.28x |
| LB `NRestarts` | 持续增长（17:49→17:51 连杀 3 次） | **0** |
| ZCode 实测 | 无响应 | **200 出字正常** |

四台 `MemAvailable` 全部回到 15-18 GiB。

**教训**：
- ⚠️ **`curl: option -d: out of memory` 与 `MemAvailable` 极低要一起看**。我留下 395MB 测试文件时
  只把它 `mv` 到「回收目录」就以为清掉了 —— 那是**磁盘**，不占内存，但确实占磁盘且误导。
  清理远端临时文件要用 `gio trash`（远端无 `mavis-trash`）。
- ⚠️ **「引擎直连正常 + 前门 503」= 先查 LB 日志**，别怀疑引擎。`journalctl --user -u glm53-lb`
  能直接给出 `killed by the OOM killer` / `status=9/KILL` 的证据。
- GB10 是**统一内存**：GPU 显存和主机内存是同一块，`nvidia-smi` 显示的 GPU 占用**同时**就是
  `free -h` 里的已用。别以为「GPU 占 101G」和「主机内存紧张」是两件事。
